# AI 智能订单管理系统

## 最终产品与技术设计说明书

-   版本：V1.1
-   用途：作为后续使用 Codex 等 AI 编程工具开发项目的基础设计依据
-   定位：可运行、可演示的 AI 业务应用，不追求生产级订单平台的复杂度

------------------------------------------------------------------------

## 1. 项目概述

### 1.1 产品定位

构建一个基于 Qwen-Max
大模型的智能订单管理演示系统。用户通过浏览器访问网页，在聊天窗口中用自然语言描述需求，也可以点击预置问题。后端通过大模型理解意图、选择业务工具，再由
Spring Boot 业务服务执行数据库操作，最后将结果反馈给用户。

核心链路：**自然语言输入 → 模型理解意图 → 选择工具 → Java 业务服务执行 →
数据库读写 → AI 组织回复 → 前端展示。**

### 1.2 核心原则

-   AI 负责理解用户需求、提取参数、选择工具和组织回复。
-   Java 后端负责参数校验、业务规则、用户数据隔离、事务和数据库读写。
-   AI 不直接访问数据库，不生成并执行任意 SQL。
-   AI 服务适配层与订单业务逻辑层解耦。
-   采用单体部署、模块化分层架构，不引入无必要的微服务和中间件。

### 1.3 明确不做的范围

-   不实现注册、密码登录、手机号验证。
-   不设置业务客户（Customer）实体或客户管理模块。
-   不设置独立商品（Product）业务表；商品名称、单价直接保存在订单中。
-   不实现真实支付、物流对接、复杂库存和复杂审批工作流。
-   不引入 Spring
    Cloud、注册中心、消息队列、Redis、分布式事务等非必要组件。
-   不建设服务端持久化的 AI 对话历史或长期记忆。

6.  不创建独立的数据统计页面，也不设置单独的统计导航入口。

## 3. 匿名访问用户与数据隔离

### 3.1 用户自动创建

系统不提供注册登录，采用匿名用户机制。浏览器使用 `localStorage`
保存后端生成的 `userId`。

首次访问：前端检查 `localStorage`；不存在 `userId` 时调用
`POST /api/users`；后端生成唯一 ID 并在 `users` 表创建记录；前端保存
ID。用户初始化完成后再加载订单和 AI 页面。

再次访问：前端读取已有 ID
并调用验证接口；用户存在则继续使用，不存在则重新创建并更新本地 ID。

用户清除 `localStorage`
或浏览器站点数据后，系统将其视为新用户。不同浏览器、设备之间不做身份同步。

### 3.2 用户标识传递

所有需要用户上下文的请求通过请求头携带：

``` http
X-User-Id: <当前匿名用户的 userId>
```

前端可通过 Axios
统一请求拦截器自动添加该请求头。后端通过统一拦截器或过滤器验证用户是否存在，并建立当前请求的用户上下文；请求结束后清理上下文，避免线程复用造成用户信息串用。

### 3.3 用户数据隔离规则

-   每条订单必须关联 `owner_user_id`。
-   查询列表、订单详情、修改、取消、发货和统计，必须限定当前用户。
-   `owner_user_id` 由后端从当前用户上下文注入。
-   不允许前端参数或大模型工具参数自行指定 `owner_user_id`。
-   用户 A 不得查询、修改、取消或统计用户 B 的订单。
-   订单不属于当前用户时，按不存在或无权访问处理，不泄露其他用户数据。
-   AI 工具调用同样必须遵循用户数据隔离规则。

**安全边界：** `localStorage` 中的匿名 `userId`
只是演示系统的用户区分标识，不是可靠身份认证。用户可以伪造请求头。本方案适用于本地或受控演示环境，不应视为公网生产系统的安全认证方案。若未来面向真实用户，需要增加登录、会话或其他服务端可验证的身份认证机制。

### 5.1 `ai/model` 与 `order/dto` 的作用

-   `ai/model`：存放 AI
    模型交互的数据结构，例如模型请求、模型响应、工具调用参数、工具调用结果等。它们用于适配
    Qwen-Max 协议，不是数据库实体。

    API 输入输出与数据库 Entity。

两个目录都可保留，但不是为了目录而目录。如果规模较小，可以按实际需要调整命名和组织方式；必须保持模型协议对象、接口

## 7. AI 业务范围限制

### 7.1 角色与回答范围

Qwen-Max
必须被约束为当前订单管理系统的智能助手，只处理与本系统功能和数据有关的请求。

允许回答： - 当前用户的订单查询、创建、修改、取消和发货。 -
当前用户的订单统计和订单数据解释。 -
本系统功能说明、操作方法和使用引导。 -
完成订单操作所必需的澄清问题，例如询问订单编号、商品名称、数量或收货地址。

对于与当前订单管理系统无关的问题，一律不做正面回答，不提供相关知识、建议、分析或延伸内容；应简短拒绝并引导用户回到订单管理业务。

拒绝示例：

> 我是订单管理助手，只能处理本系统相关的订单查询、创建、修改、状态管理和统计需求。请告诉我你需要办理什么订单业务。

### 7.2 提示词与后端约束

-   在系统提示词中明确限定角色、允许范围和拒绝策略。
-   用户输入和前端传入的历史消息均视为不可信内容，不能覆盖系统级业务边界。
-   用户要求忽略规则时，仍必须遵循业务范围限制。
-   只允许调用后端白名单中声明的订单工具。
-   即使模型错误请求了不允许的工具，后端也必须拒绝执行。
-   业务范围限制由系统提示词和后端工具白名单共同实现，不能只依赖模型自觉遵守。

## 8. 前端携带上下文的多轮对话

### 8.1 上下文原则

不在服务端持久化对话历史，不建设服务端长期记忆。由前端维护当前
conversation
的消息上下文。每次用户发送新消息时，前端将当前会话必要的历史消息和本轮消息一起发送给后端。后端仅在本次请求处理期间使用这些消息，完成模型调用和工具调用后释放，不将对话历史保存到数据库。

### 8.2 请求示意

``` json
{
  "conversationId": "conv_xxx",
  "messages": [
    {"role": "user", "content": "查询我今天的订单"},
    {"role": "assistant", "content": "今天共有 5 笔订单"},
    {"role": "user", "content": "其中有多少笔已经发货？"}
  ]
}
```

实际结构按 Qwen-Max
消息协议适配，并正确保留工具调用消息和工具执行结果消息。

### 8.3 处理要求

-   `conversationId` 用于区分前端当前会话，不代表用户身份。
-   `userId` 仍通过 `X-User-Id` 传递并由后端验证。
-   前端维护多轮历史，但应限制消息长度，避免无限增长。
-   后端校验历史消息长度、角色类型、内容大小和工具调用结构。
-   不能仅凭前端历史消息认定某项业务操作已经执行，必须以工具执行结果为准。
-   AI 识别到用户明确的写操作意图且参数完整后，直接调用写工具执行；前端只展示
    工具执行状态和真实结果，不提供二次确认交互。
-   对话上下文不落库；订单等业务数据正常持久化。

## 9. AI Tool Calling 设计

### 9.1 工作流程

1.  前端提交当前会话上下文和本轮用户消息。
2.  后端验证 `X-User-Id`，建立当前用户上下文。
3.  AI 对话服务将系统提示词、前端提供的历史消息和本轮消息发送给
    Qwen-Max。
4.  模型选择工具并返回结构化参数；信息不足时可先向用户追问。
5.  后端校验工具名称、参数 Schema 和参数值。
6.  AI Tool 层调用对应订单 Service。
7.  Service 从后端用户上下文取得 userId，执行数据隔离和业务规则。
8.  工具执行结果返回模型；模型可以继续调用工具。
9.  模型不再要求调用工具时，生成最终自然语言回复。

### 9.2 第一版工具清单

  ----------------------------------------------------------------------------------------------
  工具                    功能                    参数示意
  ----------------------- ----------------------- ----------------------------------------------
  `queryOrders`           查询当前用户订单        订单编号、状态、日期范围、商品名称、分页参数

  `createOrder`           创建订单                商品名称、数量、单价、收货地址

  `updateOrder`           修改订单                订单编号、允许修改的字段

  `cancelOrder`           取消订单                订单编号

  `shipOrder`             确认发货                订单编号

  `statisticsOrders`      统计当前用户订单        日期范围、统计维度
  ----------------------------------------------------------------------------------------------

所有工具隐式使用当前用户上下文。工具 Schema 中不得包含 `owner_user_id`。

### 9.3 多步骤任务

例如："查一下我最近的订单，如果有待付款的就取消。"

模型先调用
`queryOrders`；后端返回当前用户的查询结果；模型根据结果判断是否调用
`cancelOrder`；后端再次验证订单归属和状态后执行；工具结果返回模型，由模型汇总。

工具调用循环必须设置最大轮数，防止无限调用。

### 9.4 写操作直接执行

创建、修改、取消、发货等写操作由 AI 在识别到用户明确的执行意图后直接调用工具执行，
不需要用户二次确认：

1.  AI 从用户自然语言中提取操作类型和关键参数；信息不足时先向用户追问。
2.  后端校验工具名称、参数 Schema 和参数值。
3.  订单 Service 校验当前用户、目标订单归属和业务状态，并执行数据库写入。
4.  工具执行结果返回模型，由模型组织最终回复，前端展示真实执行结果。

约束：

-   只在用户明确表达执行意图时调用写工具；用户仅咨询或了解操作方式时，先说明，
    不调用写工具。
-   工具返回 `success=true` 才表示操作已完成，前端和模型都不得仅凭自然语言判断成功。
-   写操作失败时，模型如实转述后端返回的失败原因，不得伪造成功结果。
-   取消待执行操作记录、确认令牌和前端确认卡片机制；对话上下文仍由前端维护且不落库。

## 10. 事务管理要求

### 10.1 事务原则

一个业务动作需要执行多次数据库写入，且这些写入必须作为整体成功或失败时，必须使用数据库事务。例如一次业务操作需要新增订单并写入其他必要记录，或一次操作需要修改多条记录且要求全部成功或全部回滚。

### 10.2 事务边界

-   事务放在业务 Service 层，通常通过 `@Transactional` 管理。
-   事务只包围数据库业务操作，不包围耗时的大模型 HTTP 请求。
-   写操作由 AI 识别意图后直接执行，事务中不等待用户二次确认。
-   不把多个独立聊天轮次或多次模型调用包进一个长事务。
-   多步骤 AI 流程中，每一步工具调用完成必要校验后，由对应 Service
    管理本次数据库事务。
-   如果一个整体业务要求多项写操作原子完成，应封装成一个明确的 Service
    方法并在该方法上开启事务。

**多次 AI 调用不等于数据库事务。**
事务保证数据库写入一致性，不负责回滚已经发生的模型调用或外部 HTTP 请求。

## 11. 订单业务规则

### 11.1 订单状态

  状态编码             含义
  -------------------- --------
  `PENDING_PAYMENT`    待付款
  `PAID`               已付款
  `PENDING_SHIPMENT`   待发货
  `SHIPPED`            已发货
  `CANCELLED`          已取消

### 11.2 基础规则

-   订单编号由后端自动生成且唯一。
-   创建订单必须提供商品名称、数量和单价。
-   数量必须大于零，单价不得为负数。
-   总金额由后端使用 `BigDecimal`
    计算：`total_amount = unit_price × quantity`。
-   创建订单时由后端注入 `owner_user_id`。
-   修改、取消、发货前验证订单存在且属于当前用户。
-   已取消订单不能发货；已发货订单不能直接取消。
-   状态转换由后端 Service 统一控制。
-   修改数量或单价后重新计算总金额。
-   数据库写操作按原子性要求使用事务。
-   不实现真实支付和物流流程。

演示状态流转：待付款 → 已付款 → 待发货 →
已发货；待付款允许取消。已发货和已取消为终态。即使演示时简化付款环节，也必须保留后端状态校验。

## 12. 数据库设计

本项目只保留两张核心业务表：`users` 和 `orders`。不需要 Customer
表、Product 表，也不需要单独的用户---订单关联表。

### 12.1 users 用户表

  字段           建议类型       说明
  -------------- -------------- ----------------------------
  `id`           BIGINT，自增   数据库主键
  `user_id`      VARCHAR(64)    对外唯一用户标识，唯一索引
  `created_at`   DATETIME       创建时间
  `updated_at`   DATETIME       更新时间

### 12.2 orders 订单表

  字段                 建议类型        说明
  -------------------- --------------- -----------------------------------
  `id`                 BIGINT，自增    数据库主键
  `order_no`           VARCHAR(64)     订单编号，唯一索引
  `owner_user_id`      VARCHAR(64)     所属用户 ID，关联 `users.user_id`
  `product_name`       VARCHAR(200)    商品名称，直接保存在订单中
  `quantity`           INT             商品数量
  `unit_price`         DECIMAL(12,2)   商品单价
  `total_amount`       DECIMAL(12,2)   订单总金额
  `status`             VARCHAR(32)     订单状态
  `shipping_address`   VARCHAR(500)    收货地址
  `created_at`         DATETIME        创建时间
  `updated_at`         DATETIME        更新时间

### 12.3 用户与订单的一对多关系

-   一个用户可以拥有多条订单。
-   一条订单只属于一个用户。
-   `orders.owner_user_id` 指向 `users.user_id`。
-   可建立外键约束，保证订单所属用户存在。

``` text
users
-----
user_id (唯一键)
   1
   |
   | 一对多
   |
   N
orders
------
order_no (唯一键)
owner_user_id (外键 -> users.user_id)
```

**不需要 `user_order_relation` 之类的中间表。**
中间表通常用于多对多关系；本项目每条订单只有一个所属用户，直接在订单表保存外键即可。

### 12.4 索引与迁移

-   `users.user_id`：唯一索引。
-   `orders.order_no`：唯一索引。
-   `orders.owner_user_id`：索引/外键索引。
-   常用查询可增加
    `(owner_user_id, status)`、`(owner_user_id, created_at)` 组合索引。
-   金额使用 DECIMAL。
-   Flyway 管理建表和演示数据脚本。
-   演示数据至少包含两个用户的数据，用于验证隔离规则。

## 14. SSE 流式响应设计

后端使用 Spring MVC `SseEmitter` 向前端推送事件，模型端使用 WebClient
调用 Qwen-Max 流式接口。

  事件            用途
  --------------- ------------------
  `thinking`      AI 正在处理
  `message`       AI 回复文本片段
  `tool_call`     正在调用业务工具
  `tool_result`   工具执行结果摘要
  `error`         可理解的错误信息
  `done`          本轮对话结束

流程：前端提交当前上下文；后端验证用户并调用模型；文本片段逐步推送；出现工具调用时由后端校验并执行
Service；工具结果回传模型；最终发送 `done` 并关闭连接。

注意：工具调用结构化数据不能当普通文本输出；处理客户端断开、模型超时和工具异常；SSE
连接期间不得长时间持有数据库事务。若使用 POST + SSE，前端可用 `fetch`
读取流。

## 24. AI 服务调用可靠性设计

AI 模型服务属于外部依赖，可能出现网络波动、响应缓慢、限流、服务端故障或返回内容异常。系统必须对 AI 调用进行统一封装，不能让业务代码直接散落调用模型 API，也不能无限等待或无限重试。

### 24.1 统一调用入口

在 AI 服务适配层封装统一的模型调用客户端，例如 `QwenModelClient`。订单业务层只调用 AI 应用服务，不直接依赖 Qwen API、WebClient 或模型厂商的请求结构。

统一调用入口负责：
- 连接、响应和整体请求超时控制；
- 异常识别与转换；
- 有限重试和退避等待；
- 请求关联 ID、耗时和重试次数记录；
- 将模型厂商异常转换为系统内部统一异常。

### 24.2 超时策略

至少区分以下超时：
- **连接超时**：与模型服务建立连接的最长等待时间。
- **响应超时**：等待模型开始返回响应的最长时间。
- **整体请求超时**：一次非流式模型调用允许占用的总时间。
- **流式空闲超时**：SSE 流式调用过程中，两段数据之间允许的最长无数据时间。

建议初始配置（应根据实际 Qwen-Max 响应表现调整）：

| 配置项 | 建议初始值 | 说明 |
|---|---:|---|
| 连接超时 | 3 秒 | 建立连接过慢则终止 |
| 非流式响应超时 | 60 秒 | 等待模型响应 |
| 非流式整体超时 | 90 秒 | 限制单次调用总耗时 |
| 流式空闲超时 | 30 秒 | 连续无数据超过该时间则中断 |
| 流式整体超时 | 180 秒 | 防止流式请求无限持续 |

这些是项目初始配置，不是模型服务商保证的 SLA。超时值应集中配置，不能散落在业务代码中。WebClient 应配置连接池和相应的连接、响应超时；同时在应用层设置整体调用时限。

### 24.3 异常分类与处理

| 异常类型 | 典型情况 | 处理方式 |
|---|---|---|
| 网络瞬时异常 | 连接重置、临时网络不可达 | 有限重试 |
| 连接/响应超时 | 模型服务迟迟没有响应 | 有限重试；达到上限后返回超时错误 |
| 限流 | HTTP 429 | 优先遵循 `Retry-After`；有限重试 |
| 模型服务端异常 | HTTP 502、503、504 等 | 有限重试 |
| 鉴权异常 | HTTP 401、403 | 不重试，提示检查 API Key 和权限配置 |
| 请求参数异常 | HTTP 400 等明确的客户端错误 | 不重试，记录错误原因 |
| 模型返回异常 | 响应为空、格式不符合预期、Tool Call 参数无法解析 | 不盲目重试；按可恢复性处理并返回明确错误 |
| 业务工具执行异常 | 订单不存在、状态不允许、用户无权操作 | 作为业务错误返回，不通过重试模型调用掩盖问题 |

内部应定义统一异常类型或错误码，例如 `AI_TIMEOUT`、`AI_RATE_LIMITED`、`AI_AUTH_FAILED`、`AI_SERVICE_UNAVAILABLE`、`AI_INVALID_RESPONSE`。对前端返回可理解的错误信息，不向用户暴露 API Key、内部地址、堆栈或厂商原始敏感信息。

### 24.4 重试规则

采用**有限重试**，禁止无限重试。建议最多额外重试 2 次（总调用次数最多 3 次），使用指数退避并加入随机抖动，例如等待约 1 秒、2 秒后重试；若服务端返回 `Retry-After`，优先遵循该值，但仍受整体请求时限约束。

可以重试：
- 短暂网络连接异常；
- 连接或响应超时（仅在整体时限允许时）；
- HTTP 429；
- HTTP 502、503、504 等临时服务端异常。

不应重试：
- HTTP 400、401、403 等明确的请求或权限错误；
- 明确不可恢复的模型响应格式错误；
- 订单业务校验失败、权限失败或状态冲突。

重试策略应集中配置，并设置最大次数、最大等待时间和整体截止时间。不能在多个调用层级分别重试，造成重试次数叠加。

### 24.5 Tool Calling 与订单写操作的幂等性

模型调用重试和订单操作重试必须分开处理。模型可能在一次调用中返回创建、修改或取消订单的 Tool Call；如果后端已经成功执行工具，但后续模型总结响应失败，不能因为重试模型请求而再次执行同一个订单操作。

具体要求：
1. 每次待执行的写操作生成唯一的操作标识（如 `toolExecutionId`），同一操作的重试必须复用该标识。
2. 业务 Service 对重复操作进行幂等校验；创建订单尤其要防止重复创建。
3. 修改、取消等操作还必须校验订单所属用户和当前订单状态，必要时使用带状态条件的更新，避免重复或并发操作。
4. 工具执行成功后，应保留本次请求内的执行结果。后续模型调用失败时，可以重试模型的后续总结步骤，但不得重新执行已经成功的写工具。
5. 不能把“模型返回了 Tool Call”直接等同于“订单操作已成功”；只有业务 Service 成功提交数据库事务后，才能向用户报告操作成功。

### 24.6 SSE 流式调用的特殊处理

- 在尚未向客户端发送任何模型内容前发生可重试异常，可以按有限重试规则重新调用。
- 一旦已经向客户端发送部分内容，不能简单地从头重试并把新内容拼接到旧内容后面，否则会造成重复文本或语义错乱。
- 流式过程中发生超时、断连或模型异常时，应发送约定的错误事件（若连接仍可用），结束本次流，并让前端明确展示“本次 AI 回复中断，可重新发送”。
- 客户端断开连接后，应取消对应的模型请求，避免继续消耗模型资源。
- SSE 的重连不应默认触发一次新的模型生成或重复执行订单工具。

### 24.7 降级与用户提示

模型服务不可用时：
- 返回统一、明确的错误状态，例如“AI 服务暂时不可用，请稍后重试”；
- 不伪造模型回答，不将模型故障伪装成正常业务结果；
- 不绕过 AI 直接执行订单操作；
- 订单列表、统计等不依赖 AI 的普通业务 API 仍应正常工作；
- 若模型调用发生在订单写操作之前，失败时不得产生订单写入；若订单事务已经成功提交，则应如实保留已提交结果，不能因为后续 AI 总结失败而声称订单操作失败。

### 24.8 日志、监控与配置

每次模型调用至少记录：
- 请求关联 ID；
- 模型名称和调用类型（普通对话、Tool Calling、工具执行后的续接、流式调用）；
- 开始时间、耗时、成功或失败；
- HTTP 状态码或内部错误码；
- 重试次数及最终结果；
- Tool Call 名称和执行结果（记录必要元数据，不记录敏感内容）。

不得记录 API Key、Authorization 请求头等凭证。用户输入、模型完整输出可能包含个人或业务数据，应按最小化原则记录，必要时脱敏。

建议监控模型调用成功率、超时率、429 比例、平均耗时、P95 耗时、重试率和流式中断率。超时阈值、重试次数、退避间隔、模型地址和 API Key 均应通过配置管理，不能硬编码。

### 24.9 测试要求

至少覆盖以下场景：
- 模型正常响应；
- 连接超时、响应超时；
- 429 限流并带有 `Retry-After`；
- 502/503/504 后重试成功；
- 401/403、400 不发生重试；
- 达到最大重试次数后返回统一错误；
- 模型返回空内容或非法 Tool Call 参数；
- SSE 首段数据返回前失败，以及已经输出部分内容后失败；
- 订单写工具执行成功、后续模型续接失败时，不重复执行订单写操作；
- 客户端断开 SSE 后取消模型请求。

**实施原则：** 将超时、异常转换、重试和日志追踪统一放在 AI 服务适配层；将订单操作幂等性放在业务层；将错误状态和中断提示清晰传递给前端。两层职责不能混在一起。
